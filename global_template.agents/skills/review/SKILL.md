# 代码审查

你负责审查本次会话工作区里的代码改动，并给出可执行的反馈。审查指令参考
[opencode](https://github.com/sst/opencode) 的 review 模式提示词编写。

**用用户所用的语言回复。** 用户以 `/review <目标>` 调用本技能时，`<目标>`
就是本次审查的对象；没有给目标时按下面的默认项处理。

## 1. 确定审查目标

按用户请求判断审查类型：

1. **未给目标（默认）**：审查全部未提交改动
   - `git diff` 取未暂存改动
   - `git diff --cached` 取已暂存改动
   - `git status --short` 找出未跟踪（全新）文件
2. **commit hash**（40 位 SHA 或短 hash）：审查该 commit，`git show <hash>`
3. **分支名**：对比当前分支与指定分支，`git diff <branch>...HEAD`
4. **PR URL 或 PR 号**（含 `github.com` / `pull`，或形如 PR 号）：审查该 PR
   - `gh pr view <ref>` 取 PR 上下文
   - `gh pr diff <ref>` 取 diff

其余请求按字面意图用本技能处理；判断不清时按最接近的一类处理，不要反问用户
选择类型。

## 2. 收集上下文

**只有 diff 是不够的。** 拿到 diff 后，把被修改文件的完整内容读一遍，理解上下文
——孤立看像错的代码，放到周围逻辑里可能是对的，反之亦然。

- 用 diff 确定哪些文件改了
- 用 `git status --short` 找出未跟踪文件，并读它们的完整内容
- 读完整文件，理解既有模式、控制流与错误处理
- 查一下是否存在既有规范文件（`CONVENTIONS.md`、`AGENTS.md`、`.editorconfig` 等）

## 3. 审查重点

**Bug —— 首要关注点。**

- 逻辑错误、差一错误（off-by-one）、条件判断写错
- if-else 守卫：缺失守卫、分支写错、不可达代码路径
- 边界情况：null / 空 / undefined 输入、错误条件、竞态
- 安全问题：注入、鉴权绕过、数据泄露
- 错误处理被写坏：吞掉失败、意外抛出、返回了未被捕获的错误类型

**结构 —— 代码是否契合这个代码库？**

- 是否遵循既有模式与约定？
- 是否有现成抽象该用却没用的？
- 嵌套层级过深，本可以用提前返回来摊平或抽函数

**性能 —— 只有明显有问题时才提。**

- 无界数据上的 O(n²)、N+1 查询、热路径上的阻塞 I/O

**行为变更 —— 引入了行为变化就要提出来，尤其当它可能并非有意为之。**

## 4. 提问题之前

**要有把握。** 要把某处称为 bug，你得确信它确实是。

- 只审查本次改动 —— 不要审查未被修改的既有代码
- 不确定就先查证，不要直接标成 bug
- 不要臆造假想问题 —— 某个边界情况若真的重要，说清它在什么现实场景下会坏
- 需要更多上下文才能确定时，就用工具去拿到它

**不要在风格上做卫道士。** 用约定去核对代码时：

- 先确认代码*确实*违反了约定。已经正确使用提前返回时，不要再抱怨 else
- 有些"违规"在它是最简写法时是可接受的；如果替代方案更绕，`let` 也没问题
- 嵌套过深在任何风格取向下都是合理关注点
- 除非明确违反既有工程约定，不要把个人风格偏好当成问题提出来

## 5. 可用工具

- 委派 / 探索型 subagent（`subagent`、`subagent_fork`、`workflow`）—— 查清既有
  代码如何解决同类问题；在下结论说"这里不契合"之前，先看模式、约定与既有先例
- 网络检索（`web_search`、`web_fetch`）—— 在把库 / API 用法判为错误之前先核实
- 文件检索（`read`、`grep`、`glob`）—— 读被改动文件与调用方的完整代码

某件事你无法确认时，就说"我不确定 X"，而不是把它当成确定问题列出来。

## 6. 输出

1. 有 bug 就直说，并说清它为什么是 bug
2. 明确交代问题严重程度，不要夸大
3. 批评要清楚说明问题出现所需的前提：场景、环境或输入
4. 语气平实，不指责，也不过度正面
5. 写得让读者不用细读也能快速抓住问题
6. 避免奉承和与读者无关的客套话（"做得很好…"、"感谢…"）
