# 行文规范

## 整体原则

**注释、文档**
开发资料中，只写非显而易见的原因，描述当前状态，而非变更历史，禁止保留中间过程中的尝试，指明现行机制。

**git提交说明**
只描写最终行为，diff中看不出来的取舍、中间过程中的尝试、未合入的状态一律不要提及。主要记录上一提交的行为变更和设计思路，即变更故事/变更意图+设计思路。

## 文档编写

使用**中文**编写文档。

## 质量要求

### 结构与格式
- 输出完整文档，保持与源代码相同的结构框架：标题层级与顺序、列表类型与条目数量、有序列表起始值、表格行列、链接顺序与语义目标，以及代码块。
- 同一结构单元内，需要不同的语义分组时，段落边界可以调整。不要跨标题、列表项、表格单元格或其他独立结构单元合并或移动内容。
- 每个正文段落保持一个物理行。用段落分隔，段落内部不要硬换行。

### 一致性
- 与源代码中的每个命题保持一致，不增不减。文档中的每个句子、列表项、注释、FIXME、警告、示例、注意事项、前提条件和保证，都必须在源代码中有对应内容。两侧的列表条目数量要逐一核对。
- 行为主体、对象、条件、例外、否定、情态、因果关系，以及概念之间的区分，都要与源代码保持一致。
- 契约的确切强度与方向要与源代码保持一致。完成与生命周期条件、失败行为、方向与数据流、正常与异常结果通道、所有权变更和数量界限，不得被削弱、加强、颠倒或合并。

### 语气与风格
- 文档读起来必须像是母语为中文的技术作者直接写成的。如果某个表达像是从其他语言逐字直译而来，请改写。
- 使用适合开发者文档的专业、正式语气，绝不使用口语化或随意的表达。
- 当中文会让源代码明确陈述或明确隐含的行为主体变得模糊时，应点明该主体；不要只是为了避开被动句式而虚构责任归属。
- 优先使用成熟的中文工程术语，而不是逐字直译；用与源代码含义一致的直接描述替换比喻。
- 文本指示读者执行某项操作时，使用礼貌的祈使句。例如：称呼读者为 `你`，而不是 `您`。

### 句子结构
- 在需要停顿的地方拆分长句，避免冗长拖沓的句子。
- 主动语态能在不改变、不虚构行为主体的前提下提升清晰度时，就使用主动语态；行为主体未知、无关或有意省略时，保留被动语态。
- 为可读性可以拆分或合并分句，前提是源代码中的每个关系仍然明确。
- 不要生造母语技术作者不会使用的词语或表达。

### 用词
- 优先使用精确、正式的词汇，而不是随意或口语化的表达。
- 存在多个同义词时，选择中文专业技术文档中最常用的那个。
- 使用专有名词、规范产品名、代码标识符、API、路径、包名，以及术语表要求保留中文形式的术语。
- 结合上下文消解一词多义：一个常见词在不同技术领域并没有固定的统一译法。
- 避免俚语、内部行话或过于直译、普通开发者认不出来的表达。
- 当概念之间的区分很重要时，不要用同一个多义词描述不同的概念。
- 避免在相近位置重复同一个普通动词：如果自然的同义词能保持原意不变，就换用同义词。绝不要仅为追求文体变化而更换术语表中的形式、已定义概念或契约动词。
- 数字修饰名词时，中文语法要求的情况下应使用自然的量词。例如：「包含三种角色的能力 seam」，而不是「三角色 seam」。不要给代码、标识符、版本、单位或固定名称添加量词。

### 标点
- 中文正文使用全角中文标点：`，。：；？！（）「」`。行内代码、数字以及完整逐字引用的英文文本内，保留半角标点。
- 当冒号、句号、逗号或括号能让句子更清晰自然时，优先使用它们，而不是破折号；破折号只有在它是最清晰自然的标点时保留。
- 中文并列项之间用顿号（、），不用普通逗号。
- 列表项结尾要与其语法一致。完整句子可以句号或其他语法要求的标点结尾；列表项不要以逗号结尾。
- 中文与拉丁单词或数字之间放一个半角空格。全角标点旁不要加空格，两个汉字之间也不要有无意义的半角空格。
- Markdown 强调标记不构成词边界。根据渲染后的相邻字符确定空格：中文与中文相邻不加空格，中文与拉丁单词或数字相邻加一个半角空格。
- 数字与拉丁字母一律使用半角形式，绝不使用全角形式。
- 对于 RFC 2119 关键词（MUST、MUST NOT、SHOULD、MAY），使用对应的中文术语（必须、禁止、应当、可以）。

## 术语

下方是术语表，请严格遵守：
- 表内每个术语都要严格按照指定形式呈现。
- 如果某个术语已作为复合词的一部分释义过，之后单独出现时不要再重复释义。
- 对未列出的技术术语，若在上下文中含义明确，使用成熟的中文技术术语：采用主流中文开源项目或厂商资料中的通行译法。此规则仅适用于术语；一般行文可以自由调整结构、改写措辞以求自然表达。

## 冗余检查清单

在任何文档中都要排查以下内容：
- 同一条规则在多个归属处重复陈述。用独特短语跑一次 grep；只保留一个归属处，其余位置链接到它。
- 叙述历史或过往故事：「以前」「现在」「不再」「曾经」「改名」「迁移」、PR 或 commit 等。只陈述当前事实；需要时链接事故复盘（postmortem）。
- 正文或图表中的实现状态标注（「已实现！」「未来：…」）。状态会过时；仓库布局和包 manifest 才承载真正的状态。
- 当源码或生成器才是权威来源时，手工重述的目录、JSDoc，以及测试、包和状态的清单。
- 推理记录：逐步的实现叙述、显而易见分支的证明、测试走查，以及被否决的本地备选方案。保留最终形成的契约或可长期使用的理由；删除推导出它的路径。
- 理由在相邻的方法旁重复出现，而不是只在所属能力或辅助函数处陈述一次。
- 段落墙：一个段落承载多条规则和括号补充。把它拆开，或把细节降级到它的归属处。
- 强调泛滥：处处加粗、全大写或「至关重要」时，就没有任何重点。把强调留给改变行为的语句。

## 自查要求

写完文档后，从两个方向自查：先重读一遍，检查别扭的措辞；再逐条对照源代码，检查完整性和含义是否精确。不要包含推理记录、已通过的检查、暂定建议、撤回说明或无效修正。

**结构**
- 标题层级与顺序、列表类型与条目数量、有序列表起始值、表格尺寸和代码块内容，是否与源代码完全一致？
- 代码块内的所有注释和信息字符串，是否与源代码逐字节一致？

**一致性**
- 逐条检查：是否有内容被添加、遗漏、弱化、加强、颠倒、合并或重新界定边界？
- 行为主体、对象、条件、例外、否定、情态、因果关系、保证、契约方向、结果通道、所有权变更和数量，是否都原样保留？

**语气与风格**
- 每句话读起来是否都像母语技术作者直接写成的？
- 是否还有口语化、随意、过于非正式、宣传性或比喻性的表达？

**句子结构**
- 是否有需要拆分的冗长连写句？
- 是否有可以安全改为主动语态的生硬被动句，或虚构了行为主体的主动句？
- 条件、让步、否定、并列和修饰成分的范围是否清晰？

**用词**
- 是否有过于直译、听起来不自然的表达？
- 普通词汇在已有成熟中文表达的情况下，是否仍保留英文原词？
- 每个多义词的用法是否与其所在上下文相符？
- 是否还存在俚语或内部行话？

**术语**
- 首次出现的释义是否准确用在真正的首次出现位置，既没有遗漏也没有重复？
- 对未列出的术语，是否有可靠译法时使用成熟的中文表达、没有可靠译法时保留源术语并标记待定？

**标点**
- 标点、混排空格、引号、拉丁字母和数字是否都采用了要求的形式？
- 是否存在让句子不够清晰、应被替换的破折号？自然的破折号是否原样保留？
- 列表项结尾是否符合语法、没有以逗号结尾的？
- RFC 2119 关键词是否精确保留了源代码中的强调范围和规范强度？

### 正反案例

下面是常见问题及其修正的代表性示例。每条示例在其说明的规则内遵循"好"版本；示例不覆盖源文语境或更高优先级的要求。

**口语动词 → 专业动词**
- 坏: `仓库在 package.json 中钉住 pnpm@11.7.0`
- 好: `该仓库在 package.json 中固定使用 pnpm@11.7.0`

**长句→带有停顿的自然表达**
- 坏: `改动 packages/ 下的任何东西之前先读 docs/architecture.md。`
- 好: `在修改 packages/ 目录下的任何内容之前，请先阅读 docs/architecture.md。`

**生硬的被动语态 → 主动且自然**
- Source: `a green gate means the pair was confirmed consistent at these exact contents, not that the confirmation was sound.`
- 坏: `门禁绿意味着这对文档曾在当前内容上被确认一致，不意味着这次确认本身是对的。`
- 好: `门禁通过意味着这组文档在当前内容上的一致性得到了确认，不代表确认本身正确可靠。`

**发明的词 → 自然的表达**
- 坏: `旁挂记录两侧 blob hash，使一致性可检查`
- 好: `伴随记录保存两侧 blob hash，使一致性可检查`

**俚语/行话 → 专业表述**
- 坏: `进仓的 agent 工作流见 .agents/skills/dsh-translate-docs`
- 好: `仓库内置的 agent 工作流见 .agents/skills/dsh-translate-docs`

**“为人类”——传达的是意图，而非字面意思**
- 坏: `对于人工读者，请先从开发指南开始`（"人工读者"生硬）
- 好: `面向开发者：请先阅读开发指南`（"开发者"自然，且中文里冒号在此处更自然）
