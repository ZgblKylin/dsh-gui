# 清理推理转录泄漏

推理转录泄漏（chain-of-thought leakage）指视角落在撰写时的会话而不是仓库的文本：它引用只有该会话才看得到的产物，叙述改动而不是陈述状态，或者与一位早已离开的评审者辩论。修复不等于只删句子：只要段落承载事实分句，就先把每个分句改写成在 HEAD 处独立成立，再删掉周围的转录；不承载任何命题的段落（审计编号、控制流复述）整体删除。

改写是否安全由完整性命题规则判断：改写后的句子必须保全行为主体与动作；条件、时机与顺序；情态（必须、可以、绝不）；否定性保证与例外；以及所有权、副作用、失败模式与后果。删掉的只能是推导路径。本技能是判断框架，不是可机械执行的脚本；目录布局、排除项、检查命令与语言策略由接入的项目决定，本技能只规定判断方式。

## 唯一判据

对每个可疑段落提问：一个站在 HEAD、没有会话记录、PR 讨论和未提交草稿的读者，能否解析其中每个引用、验证其中每个论断？不能，就从仓库视角重述幸存的事实并删除其余部分；能，它就不是泄漏，无论读起来多像历史叙述。但可解析性只满足本技能的判据：在描述当前状态的载体上（README、文档、JSDoc），一段可解析的变更故事仍然是变更叙述，第 3 类会把它送到该事实的归属处。

## 泄漏类型

1. **失效的设计会话引用。**`(decision 7)`、`(audit C2)`、`design §4.7`、`plan §1.4`、阶段标签（`T4`、`W3`、`P-I`）、「设计台账」、`(B ruling)`。决策若有已提交的归属文档，按名字和路径引用它；否则删掉引用，并把它承载的事实分句重述为独立成立的陈述。
2. **栈与 PR 视角。**「本栈里靠后的 PR」「本 PR 增加了」「上一个提交」。陈述已交付的机制或扩展点；搁置的工作移到 `TODO` 标记或 issue 引用。
3. **变更叙述与版本戳。**「以前」「不再」「旧的 X」，以及指代当下的版本戳（「v1」「本次改动」「今天」，与过去状态对照的「现在」）。陈述当前行为；已修复的回归写成现在时反事实（「没有 X 时，Y 会发生」），而不是仓库历史（「以前会 Y」）。
4. **评审编排。**「评审否决：」「评审者确认了」、草稿序数（「本说明第 5 版」）、轮次归属。把幸存的决策与理由保留为普通事实；删掉谁在何时说的。
5. **面向评审者的自我辩护。**「这个 cast 是安全的，它只是……」「这是正确的，因为……」。为自身正确性辩护的注释面向评审者，不面向维护者。陈述让代码安全的不变量；如果代码本身就能显示，删掉这条注释。
6. **复述与推导记录**。控制流复述（「先做 X，再做 Y」）、测试走查、显而易见分支的证明。删除；只保留非显而易见的契约或不变量。
7. **试探语与规划残留。**「现在这样大概没问题」「应该够了」、没有标记的搁置。提升为 `TODO`/`FIXME`，或重述真实的边界；删掉试探语。
8. **撰写语言残留**。正文语言之外的工作语言碎片（英文正文里的「端」「设计稿」、`---- 私有 ----` 分隔线；中文正文里未翻译的工作片段），以及多语言对照项目里未同步的一侧。翻译或删除。判断方式取决于项目的语言策略：单语项目检查混入的异语言残留，多语言项目检查两侧是否一致。

## 不属于泄漏的内容

删除引用时不做判断，会在两个方向失败：删掉耐久的引用，留下失效的引用。以下保留规则按原样适用，[示例](references/examples.md)逐条校准：

- **issue 引用。**`#1470`、`TODO(name):`、「issue #N 拥有后续工作」在 HEAD 处可解析；任何载体都保留，包括 README，不要把它们迁进长期保留的理由文档。
- **ADR、设计说明、复盘等长期保留的理由文档里的已合并 PR 与 issue 引用**。这类文档拥有变更经过小节时，此类引用是获准的证据；是否允许变更经过小节由该项目的文档规范决定。
- **抑制注释。**`oxlint-disable … -- 理由`、覆盖忽略的理由、空 catch 的解释都是必需的文本；理由错了就修正理由，永远不要删除。
- **现在时的反事实回归表述。**「没有 X 时，Y 会发生」「一个朴素的 X 会……」；它把已修复的回归写成当前边界，而不是仓库历史。
- **测量出的边界。**「（实测：512 层嵌套约 0.15 秒）」标定常量时，「实测」标明这是数据而不是猜测，不可省略。
- **运行期的旧/新状态。**「旧连接排空后新连接才接受请求」描述运行期生命周期，不是仓库变更史。
- **长期保留的理由文档中，变更经过小节里的历史阶段名。**「第一次提交交付了 X」在那类小节里对当前状态安全；指代当下的版本戳（「本次改动」）在任何位置都被禁止。
- **按设计在仓库之外解析的外部引用**。标准章节（RFC 9110 §10.1.5）、外部设计文件里的画板名；§ 禁令覆盖的是未提交的内部草稿，不是外部标准，也不是拥有自己章节编号的提交文档。
- **项目口吻与文体形式**。以「我们」指项目；说明文档里明确标注的备选方案小节。

## 工作流

1. **确定范围与排除项**。要求调用方给出明确范围；第三方 vendored 目录、冻结的历史记录（过期归档）和生成产物不在清理范围内，具体路径由项目布局决定。录制下来的样例与快照是派生物，不是文本目标：改动拥有它们的源文件或场景，只在获得授权的行为变更需要新证据时重新生成。
2. **先只读审计**。运行[探针清单](references/recall-batteries.md)，先拿已知正例和近似误报的负例校准每条探针，再逐条语义判断命中项。探针只是探针，不是定义：每轮清理都会发现探针漏掉的案例，所以还要不依赖探针通读范围内最密集的文本（模块 JSDoc、README、设计说明）。
3. **按载体从归属处修复**。生成出来的清单与目录，追查每个消费方，改源 JSDoc 或生成器模板，再重新生成全部派生物。镜像或成对的文件（多语言对照、多处复制的同源文档），先改源侧，再按项目约定最小改动对侧；逐字代码块要按字节原样复制到两侧。模型或用户可见的字符串，只在拥有该行为的证据时才改动，否则保持原样并报告搁置。单一来源的文档，就地修改。
4. **删除前枚举命题**。先列出段落承载的命题，再对照[过度纠正陷阱](references/examples.md#过度纠正陷阱)：把义务变成认可、把假设提升为既有功能、连事实一起删掉、丢掉测量的来源。
5. **验证**。重跑探针，期望只剩获准保留的内容、本技能自身目录（它引用泄漏措辞作为校准材料）和归属文档里被引用的证据；确认剩下的每个引用在 HEAD 处可解析；运行工程现有的文档一致性与成对文件一致性检查，没有这类检查就跳过并说明。
